# Glossary and function map

Use consistent terms and locate every current page, including contextual and administrator screens.

## Terms used in PV Info
| Term | Meaning in this app |
| --- | --- |
| Source document/family | A registered regulatory publication identity whose captures/versions can evolve over time. |
| Capture | A retrieved version with original/archive and extraction metadata where supported. |
| Candidate | Extracted or discovered evidence that needs review; not an approved obligation. |
| Baseline draft | A proposed interpretation prepared from a source candidate for human review. |
| Stable requirement ID | Identity preserved across revisions of the same underlying obligation. |
| Requirement version | A specific source-linked interpretation revision with review and applicability metadata. |
| Baseline release | A versioned set of reviewed interpretations/checklist context; inspect its actual approval/publication state. |
| Applies on | Date for determining which approved interpretation is effective. |
| Known/approved by | Cutoff for review knowledge available to a historical baseline view. |
| Company portfolio | A user's confirmed company/product/market selection, separate from the public directory. |
| Match | A rules-based relevance association; not an applicability decision. |
| Ingredient naming rule | A versioned editorial naming relationship, such as the paracetamol/acetaminophen pilot; not an automatic salt/ester merge. |
| Source company role | Applicant or authorization-holder relationship recorded in a dataset; not proof of physical manufacturing. |
| Approved-change excerpt | Captured FDA safety-label change text; regulator underlining marks additions/revisions, not reconstructed deletions. |
| Recommendation index | A regulator recommendation listing requiring original-wording review; not proof of implemented product labeling. |
| Safety topic | An editorial phrase-based discovery grouping; not MedDRA, an SMQ, a validated signal or an applicability decision. |
| Reading marker | Seen/unread evidence state; not assessment or approval. |
| Human triage | A recorded review of source changes and uncertainty before company handoff. |
| Case | A company assessment/action record with pinned evidence, decisions and history. |
| Implementation draft | Business/system/process/data/training requirement derived for a company's control changes. |
| Verified closure | Recorded completion plus the available reviewer decision; distinguish independent team review from self-review. |
| Runtime snapshot | A complete generated public-data publication that can change without redeploying app code. |
| Staged | Collected product/clinical data awaits inclusion in a public runtime snapshot. |
| Published | Inspect context: a baseline publication is a human-reviewed interpretation action; a data-run publication is a successful public cache commit. |

## Substance Explorer

The public [ingredient directory](substances.html) links to [ingredient evidence](substance.html) through stable IDs. See the [Substance Explorer chapter](user-guide.html?chapter=substances) for company roles, reviewed synonyms and source coverage.

## Safety configuration specifications

Open **My Briefing → Configuration Workbench** at config-workbench.html to capture system/environment setup, compare a proposed configuration with current rules and prepare a source-linked specification. A specification is a draft implementation design, not a vendor import, executed protocol or legal approval. See the [workbench guide](config-workbench.md).

## E2B source captures and mappings

The public studio at e2b-studio.html distinguishes extracted captures, verified source records and immutable published baseline subsets. A private mapping documents a field/control in one installed system environment. A source hash change flags reassessment; it does not automatically prove a control gap. See the [E2B Studio guide](e2b-studio.md).
